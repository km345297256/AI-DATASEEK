# 科研 CASE 首轮执行恢复（2026-09-18）

## 真实故障与根因

Iris 首条 CASE 的失败会话 `4498c8619a8a4145` 不是额度或模型请求超时。工具日志显示：

1. 受管数据中 `iris.data` / `iris.names` 保留了 root 的 0700 权限。目录已登记、root 可检查，不代表实际分析用户 ubuntu 能读取。
2. 执行模型把输入核查与研究问题扩展成未请求的分类/绘图程序；传入 `--validate-only` 的程序并未在校验后提前返回。
3. 修改脚本时，`file_str_replace` 的旧字符串没有匹配，返回 `replaced_count=0`。这是已确认未写入的失败，却被归为未知副作用，整个执行因此终止。

## 通用修复

- 新任务使用独立、不可变、版本化的受管数据执行快照：文件 0444、目录 0555。原始缓存和旧任务挂载均不改动；未变化的源复用快照，源变化产生新代。
- 准备/挂载前，以镜像内实际 ubuntu 用户只读打开每个文件，验证执行端可读性。宿主路径仍需 allowlist 校验，不复制、不 chmod，不向浏览器暴露真实路径。
- 严格拒绝链接和特殊文件，检查源变化与缓存权限；准备容器无网络，不开放端口。
- 执行账本区分“尚未派发”“已确认零写入”和“副作用未知”。只有宿主派发阶段或内置文件适配器的真实响应能提供证明，插件或模型自报不能绕过保护。
- 零命中仍是真实失败，不自动重放；模型可读取文件并更正参数后继续。传输中断等真正不确定的执行仍受防重复保护。
- 所有执行路径携带当前用户请求范围。计划、路由提示和未来研究目标不构成额外分析授权。简单核查可一次执行；确有必要的 validation-only 必须实现提前退出，不能仅靠参数名称。
- 移除无条件要求分析/导出以及“不交付建议或计划”的旧提示；明确用户请求的问题定义、假设或方法设计本身可以是完整文本成果。即使不调用建模库，额外计算分类/比较指标也属于下游研究，不能从“定义问题”自动扩张。
- 统计口径需声明对象、总体、分母和比较字段；重复额外行、重复成员行和重复组数各自定义，提供可复核组大小及原始行标识，不删除或合并源记录。审核不能把打印标题当作指标定义，须与已执行方法和明细相符。
- 引用分类纠正只允许严格同源的 `context → analysis`：原段已有成功非写入结果的有效引用、文字不变、保留原成功结果锚点。失败执行、写入脚本、目录及请求不能升为分析依据。
- 当前用户请求有独立、仅限请求摘录的证据类型，不能与分析证据混用或证明执行/交付完成。历史结果投影排除这类摘录，避免后续追问把用户要求当成已发生事实。
- 实测又发现前置决策仍沿用旧的 8 秒**完整模型响应**期限，连续超时会在分析前拒绝执行。将默认单次请求等待调整为 60 秒，与答案核验保持一致；仍有限重试、仍失败封闭，不跳过安全决策，不重放分析工具。该限制不累计到分析任务时长。

不新增任务额度、时长限制或旧任务兼容处理；不放宽成果真实性核验。
